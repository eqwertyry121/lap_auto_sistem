# ТЗ v4: «Швейцарские часы» — детальная спецификация каждой фазы

> Статус: ПЛАН. Дата: 2026-08-04. Сессия-преемник.
> Выше по цепочке: `PLAN.md` (ТЗ v2, выполнено — бот жив), `PLAN_v3.md` (концепция воронки).
> Этот документ — рабочие чертежи: точные правила, формулы, схемы данных,
> метрики и критерии приёмки для каждой фазы. Любое изменение порогов —
> только через регрессионный прогон на золотой выборке (§3.6).

---

## 1. Принципы системы («швейцарские часы»)

1. **Единый источник истины (SSOT) на каждый тип данных.**
   Лоты и вердикты живого цикла — `kp_bot.db`. Знания о рынке — `research.db`.
   Эталон железа — `hw.db`. Никакой логики, читающей «из двух мест сразу».
2. **Детерминизм первичен, AI вторичен.** Gemini вызывается только там, где
   regex и математика не справились. Каждый вызов Gemini — учтён и оправдан.
3. **Каждый процесс измерим.** Счётчики по каждому слою воронки, дневной
   дайджест в Telegram. Молчание системы = инцидент (дайджест не пришёл).
4. **Каждый фильтр проверяется эталоном.** Золотая выборка ручной разметки —
   как калибр для хронометра: ни одно изменение порога не проходит без
   регрессионного теста `cmd/filtertest`.
5. **Идемпотентность и инкрементальность.** Любой процесс можно убить и
   перезапустить без потери и дублирования данных.
6. **Graceful degradation.** Челлендж KP / сеть / Gemini — система
   деградирует по известному сценарию, а не умирает.
7. **Консервативные срезы.** Лучше пропустить магазин в ручную проверку,
   чем срезать частника с «алмазом».
8. **Пороги калибруются данными, не интуицией.** Процедура калибровки — Фаза 4, веха Д.

## 2. Целевая архитектура

### 2.1 Процессы

| Процесс | Назначение | Файлы |
|---|---|---|
| `kpbot.exe` | живой цикл: опрос → воронка L0–L5 → алерты | `main.go` |
| `research.exe` | докачка деталей рынка (инкрементально) | `cmd/research` |
| `watchdog.ps1` | сторож ЖИВОСТИ процессов (по свежести heartbeat-файлов) + ротация логов (Фаза 0) | `tools/watchdog.ps1` |
| планировщик Windows | еженедельный research-скан, ежемесячный `hwdb` (Фаза 6) | Task Scheduler |

### 2.2 Данные

```
kp_bot.db    market_listings      живой цикл: лоты, статусы, вердикты, аудит алертов
research.db  research_ads         зеркало рынка (каркас + детали), пополняется ОБОИМИ процессами
             research_specs       распознанное железо (regex + Gemini, с указанием источника)
             sellers              реестр продавцов (агрегат наблюдений) — Фаза 2
             labels               золотая выборка ручной разметки — Фаза 2
             funnel_stats         счётчики слоёв воронки по дням — Фаза 0/4
             kv                   курс RSD/EUR, версия словарей и пр. — Фаза 6
hw.db        hw_cpu / hw_gpu      эталон мощности (chaynikam.info)
```

**Решение ① (непрерывное обновление рынка).** Поллер бота бесплатно видит
свежие лоты каждые 45 с. После Фазы 4 он upsert'ит их в `research_ads`
(search-уровень: цена, kpizlog, user_id, snippet) — датасет рынка стареет
медленно без отдельных сканов. `research.db` переводится в WAL-режим
(`PRAGMA journal_mode=WAL; busy_timeout=5000`), чтобы два писателя
(бот и research) не конфликтовали.

### 2.3 Воронка (порядок строго фиксирован: дёшево → дорого)

```
новый лот (search, ≤30 шт / 45 с)
 │
 L0  sanity цены          детерминирован, 0 запросов
 │   цена → EUR; 1–5000€; exchange/zamena → отсев
 │
 ├── details /eds/{id}   (только прошедшие L0; пауза FETCH_DELAY_MS)
 │
 L1  фильтр магазинов     детерминирован: метки KP + реестр продавцов + маркеры описаний
 L2  фильтр хлама         детерминирован: маркеры + condition + кросс-чек ценой
 L3  конфигурация         regex specs → (нет) Gemini-текст → (нет) Gemini-фото → 👀
 L4  цена/качество        робастная медиана конфигурации / гедоническая модель
 L5  вердикт              💎 / ✅ / ⚠️ / ❌  + объяснение + альтернативы
```

Каждый слой пишет счётчик в `funnel_stats` и причину среза — любая
деградация конверсии видна в дневном дайджесте.

## 3. Спецификация слоёв воронки

### 3.1 L0 — sanity цены (нулевая стоимость)

**Вход:** `SearchAd` (search-уровень). **Выход:** `PASS` / `REJECT_L0:<причина>`.

| # | Правило | Формула / источник | Действие |
|---|---|---|---|
| 0.1 | Валюта в EUR | `toEUR()` (таблица курсов §6.3) | нормализация |
| 0.2 | Диапазон | `1 ≤ eur ≤ 5000` | вне → REJECT (`PRICE_FLOOR` / `PRICE_CEIL`) |
| 0.3 | Обмен | `exchange == true` в search-JSON **или** `zamena` в заголовке/snippet | REJECT (`EXCHANGE`) |
| 0.4 | Фейковая цена витрины | мультилистинг (§3.2, правило М4): заявленная цена не относится к конкретному ноутбуку | лот идёт в L1 как витрина, в медианы НЕ попадает |

**Решение ② (бесплатные сигналы с поиска).** Текущий `SearchAd` выбрасывает
поля, которые KP уже отдаёт на уровне поиска: `kpizlog`, `condition`,
`exchange`, `is_renewed`, `last_renew`, `view_count`, `description_snippet`,
`location_name`. Расширить модель и сохранять их в `research_ads` —
половина сигналов L1/L2 доступна БЕЗ запроса `/eds/`.

**Исключения:** сетевая ошибка/челлендж на search — НЕ решение L0;
обрабатывается эксплуатационным слоем (§5.0.1).

### 3.2 L1 — фильтр магазинов

**Вход:** лот с деталями + запись реестра `sellers[user_id]`.
**Выход:** `PRIVATE` / `SHOP` / `UNKNOWN` + причины (список сработавших правил).
`UNKNOWN` трактуется как `PRIVATE` (принцип 7).

Правила (выполняются до первого решающего; вес каждого — в счётчике продавца):

| Код | Правило | Источник сигнала | Сила |
|---|---|---|---|
| М1 | KP пометил торговца | `user.trader != nil` | решающее → SHOP |
| М2 | Витрина KP Izlog | `kpizlog == true` (search или /eds/) | решающее → SHOP |
| М3 | Конвейер продавца | активных лотов продавца ≥ 5 (реестр `sellers`) | решающее → SHOP |
| М4 | Мультилистинг-прайс | ≥3 строк вида `#NN-…€` или ≥4 строк `… | … | …€` с ценами | решающее → SHOP + `PRICE_FAKE` |
| М5 | Маркеры описаний | словарь §8.1, взвешенная сумма ≥ порога T_L1 | решающее → SHOP |
| М6 | Молодой аккаунт-оптовик | аккаунт < 90 дней И лотов ≥ 3 | поддерживающее (+к счёту М3) |

**Реестр `sellers`** (ключ — `user_id`, который есть уже в search-ответе):
```sql
CREATE TABLE sellers (
  user_id      INTEGER PRIMARY KEY,
  first_seen   INTEGER, last_seen INTEGER,
  ads_seen     INTEGER,              -- сколько раз продавец встречен
  trader_seen  INTEGER, kpizlog_seen INTEGER,
  reviews      INTEGER,              -- из последнего /eds/
  user_created TEXT,                 -- дата регистрации аккаунта из /eds/
  verdict      TEXT,                 -- SHOP/PRIVATE/UNKNOWN (кэш решения)
  label        TEXT                  -- ручная разметка (золотая выборка)
);
```
Частник продаёт 1–2 ноутбука; ≥5 одновременных лотов — промышленный
масштаб, независимо от меток KP (охота на «хамелеонов» из рисков v3).

**Метрики фазы (DoD §5.2):** recall ≥ 0.95, precision ≥ 0.90 на золотой
выборке 50 продавцов; ложных срабатываний на размеченных PRIVATE ≤ 5%.

### 3.3 L2 — фильтр хлама

**Вход:** лот после L1 (PRIVATE/UNKNOWN). **Выход:** `CLEAN` / `PARTS_ONLY` /
`DEFECT` / `BROKEN_UNCERTAIN`.

Два класса маркеров (важно не смешивать):

| Класс | Смысл | Действие |
|---|---|---|
| `PARTS_ONLY` | продажа запчастей/трупа | жёсткий блок: лот не идёт в L4 и медианы |
| `DEFECT` | рабочий, но с дефектом (батарея, экран, клавиатура) | мягкий: ⚠️ CHECK, в медианах участвует с пометкой |

**PARTS_ONLY** (заглавный список, уточняется частотным анализом):
`neisprav*, pokvaren, ne radi, neupaljiv, za delove, za dijelove, za rezervne,
defekt*, oštećen/ostecen, broken, faulty, parts only, za otpad, ne pali se,
ne puni se, mrtav, ne daje sliku` + `condition == "broken"` (если появится).

**DEFECT**: `baterija (ne drži|slaba|crkla), zaliven, pukao ekran, mrtvi
pikseli, ne radi tastatura|touchpad, bez punjača|bez diska, šarka|pant
slomljen, fleke na ekranu`.

**Кросс-чек ценой:** `PARTS_ONLY`-маркер + цена внутри распределения
конфигурации → вероятна ошибка маркера (слово в цитате/описании модели) →
`BROKEN_UNCERTAIN` → ⚠️ CHECK, а не тихий блок. Обратное: цена < 40% медианы
конфигурации без маркеров → принудительный ⚠️ CHECK (скам или скрытый дефект).

**Метрика:** 100% размеченных «za delove / neispravan» не проходят в алерты
(нулевая терпимость к пропуску трупов).

### 3.4 L3 — конфигурация

Ступени (каждая следующая — только если предыдущая не дала CPU с баллом):

1. **regex** (`specs.Extract`, уже есть + расширения §5.5.4) — 0 токенов;
2. **Gemini-текст**: описание + `attrs_json` → JSON
   `{"cpu":"…","ram_gb":N,"ssd_gb":N,"gpu":"…"}` — 1 вызов;
3. **Gemini-фото**: до 5 фото, фокус на наклейки/шильдики (уже в evaluator) —
   1 вызов + фото;
4. **терминал**: `👀 ПОСМОТРИ САМ` (NEED CHECK без вердикта).

Результат каждой ступени пишется в `research_specs` с источником:
`source ∈ {regex, gemini-text, gemini-photo-all}` — рынок учится, повторные
вызовы по тому же лоту запрещены (идемпотентность).

### 3.5 L4 — цена/качество (ядро математики)

**Группировка (иерархия ключей):**
```
K0 = cpu_model + ram_band + ssd_band + gpu_present   (цель)
K1 = cpu_model + ram_band                             (упрощение)
K2 = cpu_model                                        (упрощение)
K3 = гедоническая модель (регрессия, см. ниже)        (универсальный fallback)
```
`ram_band`: 2/4/8/16/24/32/48/64/128 (точно), `ssd_band`: 128/256/512/1024/2048.
Группа используется, если `n ≥ 8` (K0) / `n ≥ 5` (K1, K2); иначе вниз по иерархии.

**Робастная медиана (двухпроходная):**
```
m1 = median(prices)                       # все EUR-лоты группы, 1–5000€, возраст ≤ 60 дней, без SHOP/PARTS_ONLY
MAD = median(|p − m1|)
σ̂  = 1.4826 · MAD
m2 = median(p : |p − m1| ≤ 3σ̂)            # финальная медиана без выбросов
```
Исходные пороги отсечения (калибруются, Фаза 4 веха Д): `n` ≥ 5, отклонение алмаза
`dev ≤ −15%`, где `dev = price/m2 − 1`.

**Решение ③ (гедоническая модель вместо «медианы по больнице» для редких
конфигураций).** Простая OLS-регрессия без внешних библиотек (~60 строк Go,
нормальные уравнения + метод Гаусса):
```
price_eur = β0 + β1·(cpu_score/1000) + β2·ram_gb + β3·(ssd_gb/256) + β4·(gpu_score/1000)
обучение: kind=USED, PRIVATE, 10–5000€, cpu_score>0, возраст ≤ 90 дней
использование: только при R² ≥ 0.60 (иначе лог и пропуск); предсказание = m3
```
Даёт предсказание цены для ЛЮБОЙ конфигурации (даже n=1) и единый масштаб
«дорого/дёшево». β и R² пишутся в `kv` + в дайджест — дрейф рынка виден.

**Альтернативы (обязательная часть алерта):**
- A1: то же железо дешевле (`cpu` тот же, цена ≤ −5% от лота), топ-3 по цене;
- A2: мощнее за те же деньги (`cpu_score ≥ 1.2×`, цена ≤ +10%), топ-3 по баллу;
- A3: лучший €/1000 баллов в цене ±20% (топ-3).

**Антискам-предохранитель:** `dev < −40%` → вердикт не 💎, а
`💎? ПОДОЗРИТЕЛЬНО` + плашка «проверь продавца» (аккаунт < 30 дней или
0 отзывов усиливает подозрение). Приманки не должны выглядеть как алмазы.

### 3.6 L5 — вердикт (детерминированная сборка, не AI)

| Код | Условие | Telegram |
|---|---|---|
| 💎 `DIAMOND` | PRIVATE ∧ CLEAN ∧ cpu_score>0 ∧ dev ≤ −15% ∧ n ≥ 5 ∧ нет A2-альтернативы ∧ dev ≥ −40% | ALERT |
| 💎? `DIAMOND_SUSPECT` | как DIAMOND, но dev < −40% или продавец «молодой» | ALERT с плашкой |
| ✅ `FAIR` | −15% < dev ≤ +10% | тихо (только БД) |
| ❌ `EXPENSIVE` | dev > +10% | тихо |
| ⚠️ `CHECK` | DEFECT / BROKEN_UNCERTAIN / цена вне распределения / exchange-сомнения | NEED CHECK |
| 👀 `MANUAL` | конфигурация не распознана даже Gemini (терминал L3) | NEED CHECK |

Объяснение собирается из данных: «i5-1135G7 (балл 10 300) · 16GB/512GB ·
медиана конфигурации €300 (n=14) · цена €240 = −20% · альтернативы: …».
Никакой генерации текста моделью — только факты (воспроизводимость, ноль
галлюцинаций в алерте).

**Золотая выборка (`labels`):** ≥ 50 продавцов (25+ SHOP, 25+ PRIVATE) и
≥ 30 лотов хлама; источник истины для любых изменений словарей/порогов.
`cmd/filtertest` гоняет воронку по выборке и печатает precision/recall —
обязательный шаг перед деплоем любого изменения фильтров.

## 5. ТЗ по фазам

### Фаза 0 — Надёжность и наблюдаемость (ПРЕД-РАБОТА)

Смысл: сначала приборная панель и автопилот, потом усложнение. Часы без
секундной стрелки не настроишь.

Ключевое решение Ф0: **проверяем живость, а не наличие**. Наличие процесса
в списке ОС ничего не доказывает: зависший kpbot (дедлок планировщика,
вечный HTTP-запрос) выглядит «живым», но работу не делает. Единственный
критерий живости — свежесть heartbeat-файла, который процесс обязан писать
сам, из отдельной горутины.

| # | Работа | Детали |
|---|---|---|
| 0.1 | Челлендж-бэкофф живого бота | Сейчас при `areYouHuman` на search бот ломится каждые 45 с (пустые запросы, продлевает челлендж). Правило: `ErrChallenge` на search → пауза `CHALLENGE_PAUSE_MIN=30` (env), одна WARN-запись. Реализация: трекер в `main.go` (`pausedUntil time.Time`). |
| 0.2 | Heartbeat-дайджест (для человека) | Раз в сутки (09:00) бот шлёт в Telegram: аптайм, лоты за 24ч по статусам, челленджи, покрытие research.db (читает read-only), последние алерты. Старт/стоп процесса — тоже сообщение. Нет дайджеста = бот мёртв, видно без мониторов. |
| 0.3 | Heartbeat-файлы (для машины) | kpbot и research заводят фоновую горутину: раз в 60 с пишет `data/kpbot.heartbeat` / `data/research.heartbeat` — unix-время + состояние (`polling` / `challenge_pause` / `fetching`). Горутина независима от основного цикла: heartbeat остаётся свежим даже во время 30-минутных антибот-пауз. Запись остановилась → процесс фактически мёртв (дедлок), сколько бы он ни висел в списке ОС. |
| 0.4 | Watchdog по живости | `tools/watchdog.ps1`: каждые 10 мин (Task Scheduler) проверяет СВЕЖЕСТЬ heartbeat-файлов, а не `Get-Process`: `kpbot.heartbeat` ≤ 3 мин, `research.heartbeat` ≤ 15 мин. Три исхода: (а) файла нет/процесса нет → ротация лога + запуск; (б) процесс есть, heartbeat протух → завис: kill + ротация лога + запуск; (в) всё свежо → ничего. Команды запуска — из HANDOFF. Свои действия пишет в `data/watchdog.log`. |
| 0.5 | Ротация логов | `Start-Process -RedirectStandardOutput` сейчас ПЕРЕЗАПИСЫВАЕТ лог при перезапуске — история теряется. Ротация в watchdog решает (`.1` ← текущий). |
| 0.6 | Регрессия | `go build ./... && go vet ./... && go test ./...` — зелёные; smoke: дайджест дошёл в Telegram. |

**DoD Ф0:** бот переживает челлендж без спама ошибками; дайджест приходит;
и УБИТЫЙ, и ЗАВИСШИЙ процесс поднимается watchdog'ом ≤ чем за 10 минут
(зависший детектируется по протухшему heartbeat-файлу, а не по наличию
процесса); логи не теряются.

### Фаза 1 — Данные (идёт)

Докачка деталей всех лотов. Вехи и действия на каждой:

| Веха | Действие |
|---|---|
| каждые 1000 описаний | `go run ./cmd/research -enrich` + `go run ./tools/dbstatus` (покрытие) + запись в HANDOFF |
| 1000 описаний | зелёный свет Фазе 2 (частотный анализ уже репрезентативен) |
| ≥ 95% рынка | финальная калибровка порогов L4 (Фаза 4, веха Д) на полном рынке |

**Решение ④ (приоритизация докачки).** Свежие лоты полезнее старых для
медиан: research при выборе следующей страницы идёт по `posted DESC`
(страница 1 = свежие) — порядок уже правильный, не менять; при перезапуске
строки `SEARCH` на страницах 1–30 обновляются первыми автоматически.

**DoD Ф1:** `fetch_status='OK'` ≥ 1000 → старт Ф2; ≥ 95% рынка → финал Ф4/калибровка.

## 6. Сквозные требования

### 6.1 Тестирование
- Unit: чистые функции фильтров/математики — табличные кейсы, реальные строки
  из датасета (включая диакритику сербского и мусорные вход).
- Регрессия фильтров: `cmd/filtertest` на золотой выборке — обязательный
  шаг ЛЮБОГО изменения словарей/порогов.
- Бэктест: `cmd/analyze -replay` перед деплоем изменений воронки.
- Live-тесты: существующие `-tags live` — только вручную.

### 6.2 Наблюдаемость
slog (уже везде) + `funnel_stats` + дайджест + `tools/dbstatus`. Правило:
любой процесс обязан оставлять след за последние 24ч (лог/счётчик/дайджест).

### 6.3 Курсы валют (`toEUR`)
EUR: 1 · RSD/DIN: курс из `kv` (fallback 117.2) · BAM/KM: 1.95583 ·
USD: 0.92 (обновляемо через `kv`). Единая функция — один владелец
(`pricing/currency.go`), ноль дублей по коду (сейчас константа сидит в
`cmd/analyze`).

### 6.4 Антибот-гигиена
Все запросы к KP — только через существующие клиенты (подпись, ротация UA,
паузы). Никаких новых эндпоинтов без проверки нагрузки. Бюджет деталей
research не увеличивать (100–150/час — эмпирически безопасный).

### 6.5 План Б: эскалация антибота KP (лестница, а не импровизация)

Весь конвейер данных висит на эмпирическом бюджете (~100–150 деталей/час).
Если KP закрутит гайки, система не импровизирует — она поднимается по
заранее заданной лестнице. У каждого уровня: детектируемый триггер (по
логам/дайджесту, а не «по ощущениям») и готовое действие. Бюджет запросов
на любых уровнях ТОЛЬКО снижается, никогда не растёт.

| Уровень | Триггер | Действие |
|---|---|---|
| L0 норма | челленджи ≤ 2 за сутки | текущий режим: `detail-delay-ms=3000`, `page-delay-ms=1500` |
| L1 ужесточение | челлендж в каждом цикле research / детали стоят 6+ ч | задержки ×2 (6000/3000), бюджет пополам; research — только ночными окнами; живой бот работает как работал |
| L2 детали недоступны | `/eds/` не отвечает 24+ ч при живом search | бот деградирует на search-уровень (Решение ②): L0 + частичный L1 по search-сигналам + вердикт по title/snippet; алерты с плашкой «детали недоступны»; research на стоп до снятия |
| L3 блокировка IP | 403/челлендж на всё, включая search | ротация IP: перезапуск роутера (динамический IP) → тетеринг с телефона (мобильный IP). Прокси — крайняя мера (может испортить репутацию сильнее) |
| L4 структурные изменения | 401/падение декода JSON/смена полей (регрессия подписи и тесты декода это заметят сразу) | стоп обоих процессов, уведомление в дайджесте, ручное обновление клиента (соль подписи/схема) |

Правила лестницы: переход вверх — по триггеру; каждое действие фиксируется
в `data/watchdog.log` и в ближайшем дайджесте; после снятия челленджа
возврат на L0 автоматический (задержки — конфигурация, не код). Смысл
уровней L2+: даже в худшем случае живой бот продолжает приносить пользу
(алерты по search-сигналам), а не молчит.

## 7. Definition of Done всего проекта (ужесточённый v3)

1. Магазины и хлам: 100% срез на золотой выборке ДО Gemini (`filtertest`).
2. Каждый алерт: конфигурация, отклонение от медианы (n), 2–3 альтернативы
   со ссылками, вердикт-эмодзи; аудит сохранён в БД.
3. Вердикт по лоту из Telegram: `go run ./cmd/analyze -lot <id>` даёт цифры
   (медиана/отклонение/альтернативы) по полному рынку.
4. Медианы по конфигурациям, полный рынок, автообновление (недельный цикл).
5. Надёжность: неделя автономной работы без человека (Ф6) — дайджесты,
   watchdog, очередь алертов, курс.
6. Экономия: ≥ 70% вызовов Gemini относительно базовой линии.
